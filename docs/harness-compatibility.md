# Harness compatibility

## Supported versions

| Component | Admitted Harness versions |
| --- | --- |
| Connections 0.1.10 on the local Host | Exactly `0.2.1-rc.5` |
| Remote content bundle | `0.2.1-rc.2`, `0.2.1-rc.3`, `0.2.1-rc.5` |
| New managed installation | Starts with `0.2.1-rc.2` |
| Explicit remote update default | Latest admitted version, `0.2.1-rc.5` |

For a local rc.3 Host use Connections 0.1.7; for rc.2 use 0.1.0. Installing the
local plugin does not upgrade a running remote Harness. rc.4, 0.2.2-alpha.2 and
future versions are not admitted by this release.

## Version policy and automatic admission

The exact local gate reflects the remaining version-bound adapters. Build input
versions, admitted installations and versions exercised by CI are separate facts;
a matching plugin protocol alone does not establish native runtime compatibility.

Both browser artifacts reject Harness Client runtime module imports. Native
Service/Slot contracts remain build inputs, with these integration boundaries:

| Boundary | Ownership and checks |
| --- | --- |
| Local sidebar | Independently deployed by Harness; no copied factory or CSS. Connections contributes its workspace list and Settings header through slots. Conflicting providers cause those contributions to withdraw. |
| Shortcut routing | Native provider, keybindings and dispatch remain installed. A checked private `registry.commands` adapter wraps content and Settings resolvers; failure closes or refuses remote views and preserves local commands. |
| Remote Settings | One version-checked ConfigForms constructor adapter projects local interface preferences before native consumers start. Execution forms retain native schemas and write queues. |
| Remote Account | Independently deployed native provider, components and CSS; public slot delegation adapts sign-in presentation and browser open/copy. |
| Remote layout | A dedicated content profile replaces native layout/settings providers and selects the native browser directory picker. It is not a general multi-Host composition API. |
| Host integration | Native launch-log parsing, browser authentication and Plugin Manager envelopes remain version-bound. |

`dist/native-inputs.json` records native versions and SHA-512 input digests.
`dist/contracts.json` records plugin-owned contracts and their relationship to
those inputs. Both are generated by the build and shipped in the package;
[NOTICE](../NOTICE) records adapted code and licenses. Settings sources for
rc.2/rc.3/rc.5 are compared before sharing an adapter; changed inputs fail the
build and require review.

The open-view handshake checks required workspace, surface, Settings and Account
contracts before navigation. A mismatch produces an update instruction while
preserving healthy SSH and local management. Version 0.1.9 requires Settings and
Account content revision 2; update older remote content and reopen it. Managed
connections reconcile their content bundle without implicitly upgrading Harness.

Broader admission needs public navigation, command-resolver and pre-consumer
Settings hooks, plus native acceptance. A bare lower-bound range would also admit
future prereleases and incompatible versions. See [roadmap](roadmap.md).

## Desktop remote content and commands

Remote workspaces and Settings use Harness's native version-1 guest lease bridge
with acquisition, release and popup subscription. Browser access requires HTTP
localhost/127.0.0.1 on the local Harness computer; a custom URL scheme alone does
not establish Desktop support.

The embedded layout does not declare or mount `shell.leading`: its sidebar and
New Session buttons belong to the outer application. Native content, rightbar,
bottom and overlay slots remain available; Settings mounts the native sidebar
under a hidden container to retain its dialog and slot lifecycle. A declared
slot is not an instruction to display window chrome unconditionally.

The list's New Session action and keyboard command follow the selected Host;
the native top New Session button returns to the local Host. Search/add use the
unified list, and Close dismisses the selected remote surface. Commands without
safe remote delegation show guidance to use native remote controls, leaving the
hidden local session untouched. See [usage](usage.md) for navigation behavior and
[development](development.md#acceptance-boundaries) for platform coverage.

## Updating an open rc.3 Desktop

Connections 0.1.5 replaced the native shortcut provider and could blank an open
rc.3 renderer when enabling the plugin. Version 0.1.6 removed that replacement.
Retiring an active 0.1.5 provider may still require one renderer reload after
installation. Save unsent drafts first; Connections never reloads automatically.
A local or remote Host restart is not required for that renderer failure.

If an old installation moved `stopSequenceMs` into Connections, restore it to the
native `shortcuts` deployment. User keybindings remain in native storage.

## Migrating earlier installations

Versions 0.1.2–0.1.8 used a copied sidebar adapter. Version 0.1.9 leaves the native
sidebar independently installed. Save drafts before upgrading an active old
patch; a running loader may need one refresh to retire the previous composition.

The unpublished `@xunz/dsh-connections` bundle must not coexist with
`@xunz03/dsh-connections`. After active tasks finish, stop the intended Host and
use its same homes, runtime and profile:

```sh
dsh plugin --profile web remove @xunz/dsh-connections
dsh plugin --profile web add @xunz03/dsh-connections
```

Restart that Host. For a managed remote, remove the old bundle using the
[managed service's homes/runtime](host-settings.md#installing-and-managing-remote-plugins),
then reconnect to install the matching remote content bundle. Preserve managed
data, credentials and browser storage; their internal ownership identifiers
remain stable. Do not install the full local package into a content-only profile.
